1|Smoke testing is a quick check that the build is stable enough to test further, for example login and the main page open. Sanity testing is a narrow check after a small fix to confirm that one change works. Regression testing re-runs a wide set of old tests to confirm that new changes did not break existing features. I run smoke on every build, sanity after a hotfix, and full regression before a release.
2|I automate tests that are repeated often, stable, high risk and data heavy, such as login, checkout, API contracts and cross-browser checks. I do not automate one-time tests, features that change every sprint, or visual judgement checks. I compare the time saved against the cost of writing and maintaining the script, and start with the smoke and regression core.
3|First I find why it is flaky instead of adding retries. Usual causes are timing, unstable locators, shared test data and test order. I use explicit waits on conditions, stable locators such as data-test ids, and make every test independent with its own data. If a test is still flaky I quarantine it so it does not block the build, log a ticket, and fix the root cause within a set time.
4|Page Object Model keeps the locators and actions of each page in one class, and the tests only call those methods. If the UI changes, I fix one page class and not fifty tests. Example: a LoginPage class with login(user, password), and every test calls it. It makes tests shorter, readable and cheaper to maintain.
5|I send the request with Postman or RestAssured and check the status code, the response body against a schema, important headers, and response time. I also test negative cases like missing fields, wrong types, expired token and no permission, and check that repeating a PUT or DELETE is safe. For data changes I confirm the result in the database or with a follow-up GET.
6|I choose the language the team already knows, for example Java with Selenium or TypeScript with Playwright, and a test runner like TestNG or Playwright Test. Structure: page objects, reusable helpers, test data layer, config per environment, and reports such as Allure. Tests run in parallel in CI, in a clean environment, with tags for smoke and regression. I start small with the critical flows, then grow it, and review flaky tests every week.
7|The pipeline runs smoke tests on every commit, API and integration tests on merge, and full regression nightly or before release. A build is blocked if smoke or critical tests fail. Flaky tests are quarantined by a clear policy so they do not block everyone. Results go to a dashboard and the team channel, and the owner of the failing change is notified.
8|Example (use your own): "On a [project] we found a [payment rounding] bug one day before release. I reproduced it, wrote clear steps with logs, and told the developer and product owner at once. The fix went in the same day and we retested the full flow. After that I added an automated check for that case and a review step in the test plan so similar issues are caught earlier." Finish with the lesson.
9|I stay calm and reproduce the failure myself. I share logs, screenshots, the exact steps and the expected result from the requirement. If it is truly a test problem, I fix it quickly and thank them. If it is a bug, I show the evidence and sit with the developer for ten minutes to debug together. The goal is a correct product, not winning the argument.
10|I do not decide by feeling. I sort the failures by risk: which are in critical flows like payment and login, which are known flaky tests, which are test data issues. I re-run the suspect ones. Then I give a clear recommendation with numbers, for example "3 real bugs in checkout, so no-go, the rest are flaky". The business owner takes the final decision with that data, and I document it.
11|An interface defines a contract with no state, and a class can implement many interfaces. An abstract class can have fields, constructors and shared code, but a class can extend only one. Since Java 8 interfaces can have default methods. I use an interface when unrelated classes share behaviour, and an abstract class when related classes share state and code.
12|== compares references, whether two variables point to the same object. equals() compares the content when a class overrides it. The contract: if two objects are equal, they must return the same hashCode. If you override equals() and not hashCode(), HashMap and HashSet will not find your objects correctly.
13|HashMap stores entries in an array of buckets chosen by the hash of the key. Equal hash buckets hold a linked list of entries. Since Java 8, a bucket with many entries turns into a balanced tree, so worst-case lookup is O(log n) instead of O(n). It resizes when the load factor of 0.75 is crossed. It is not thread-safe; use ConcurrentHashMap for concurrent use.
14|Spring Boot scans the classpath, and starters bring in dependencies. Auto-configuration creates beans only when conditions match, for example when a DataSource class is present and you have not defined your own. Dependency injection means Spring creates objects and passes them in, preferably through the constructor, so classes are loosely coupled and easy to test with mocks.
15|synchronized gives mutual exclusion and visibility with a simple block or method. volatile only guarantees visibility of one variable and no caching in threads, but not atomic compound actions like count++. ReentrantLock gives more control: tryLock, timeouts, fairness and multiple conditions. I use volatile for flags, synchronized for simple critical sections, and ReentrantLock when I need those extra features.
16|I watch heap usage and GC logs to confirm heap keeps growing. Then I take a heap dump with jmap or on OutOfMemoryError, and open it in Eclipse MAT or VisualVM to see which objects are retained and by what. Common causes are static collections that never clear, unclosed resources, listeners not removed and ThreadLocals. I fix the reference, add a test or a metric, and watch heap after deployment.
17|Keep the service stateless so I can run many instances behind a load balancer. Use connection pooling, indexes and caching with Redis for hot reads, and async or queues for slow work. Add rate limiting, timeouts and circuit breakers. Measure with load tests, and expose metrics, logs and tracing so I can see bottlenecks. Scale horizontally first, then tune the database.
18|Example (use your own numbers): "A report API took 8 seconds. I profiled it and found an N+1 query problem. I used a join fetch and added an index, and cached the stable part. Response time dropped to 900 ms, and I added a load test to guard it." Always say how you measured before and after.
19|First, check if rollback is the fastest safe step, since users are affected. Look at the dashboard for error rate and the logs for the stack trace, and compare with what changed in the deployment: code, config, database migration. Tell the team and stakeholders a short status. After the service is stable, I find the root cause and write a short post-incident note with the prevention step.
20|I first understand the real business need behind the request. Then I explain the technical impact in simple words, with options and costs: the exact request, a simpler alternative, or a phased approach. I record the decision in writing. If the client still wants it, I raise the risk with my manager, but I do not just say no.
21|A list is ordered and changeable. A tuple is ordered and fixed, good for records and dictionary keys. A set holds unique values with fast membership checks. A dict stores key-value pairs with fast lookup by key. Example: use a set to remove duplicates, a dict to count words, a tuple for coordinates.
22|A decorator is a function that wraps another function to add behaviour without changing its code, for example logging, timing or authentication checks. A generator uses yield to produce values one at a time, so a big file can be read line by line without loading all of it into memory. I used them for [your use case, e.g. a timing decorator and a CSV reader].
23|The GIL lets only one thread run Python bytecode at a time in CPython. So threads do not speed up CPU-heavy work. For CPU-bound jobs use multiprocessing or native libraries like NumPy. For I/O-bound work like API calls or file reads, threads or asyncio work well because they wait most of the time.
24|I separate layers: routes or views, services with business logic, and a data layer. Settings come from environment variables, with separate configs per environment. I use dependency injection in FastAPI, migrations for the database, linting and type hints, and tests in CI. A clear folder structure and a README help new team members start fast.
25|I write small functions with clear inputs and outputs and keep business logic apart from I/O. I use pytest with fixtures. I mock external boundaries like HTTP calls, payment gateways and time, but not my own business logic or the database layer where an in-memory or test database is possible. Too many mocks make tests fragile.
26|I measure first. tracemalloc or memory_profiler shows where memory is allocated. Common causes are loading whole files or query results into lists, caches that never expire and references kept in globals. Fixes: generators, chunked reads, pagination, __slots__ or a bounded cache. Then I confirm memory stays flat under load.
27|Producers put jobs on a queue like Celery with Redis or RabbitMQ. Workers retry with exponential backoff and a maximum count. Each job gets an idempotency key so repeating it does not charge or send twice. After the maximum retries it moves to a dead-letter queue with alerts. I add monitoring for queue length and failures.
28|Example (use your own): "A script gave wrong totals only on some days. I added logging and found a timezone issue in date comparison. It took a day because it only happened near midnight. I fixed it with UTC dates, added a test for that case and wrote the finding in the team notes." Show your method: reproduce, narrow, test.
29|I stop loading the whole file. I stream it line by line or in chunks with a generator or pandas chunksize, process and write results as I go, and keep a checkpoint so a rerun can continue. I also add error handling for bad rows and log the progress.
30|I first add a few characterization tests around the part I will change so I know the current behaviour. Then I make small safe steps, avoid wide refactors, and keep changes reviewable. I tell my manager clearly what is risky and what is not covered by tests, and add tests for the new feature itself.
31|Functional requirements say what the system does, for example "a user can reset a password by email". Non-functional requirements say how well it does it, for example "pages load in under 2 seconds" or "supports 5,000 users at once". Other examples: security, availability, accessibility. Both must be testable.
32|I start with a business requirements document or project brief, then stakeholder lists, process flows for as-is and to-be, user stories with acceptance criteria, wireframes, and a requirements traceability matrix. During testing I support UAT scripts and sign-off, and after go-live a change log. I pick the artifacts that fit the project size.
33|I write stories in the form "As a [user], I want [goal], so that [value]" and check them against INVEST: independent, negotiable, valuable, estimable, small and testable. Acceptance criteria use Given-When-Then, for example: Given a registered user, when they enter a wrong password three times, then the account is locked for 30 minutes.
34|I use MoSCoW (must, should, could, won't) together with business value versus effort. I sit with the sponsor and key stakeholders to explain the trade-offs: if this goes first, that moves later. Then I record the agreed order and the reason in the backlog so everyone sees the same priority.
35|I use walkthroughs and prototypes or wireframes so people react to something concrete. I send a written summary, collect feedback, update the document and ask for formal sign-off. After that, changes go through change control with impact on time and cost.
36|I interview the people who do the work and observe the current flow to draw the as-is process. I mark pain points, delays and manual steps, and find the gaps against the goal. Then I design the to-be flow with fewer steps, clear owners and system support, and define KPIs such as onboarding time and error rate. I validate both with stakeholders.
37|Example (use your own): "Sales and operations wanted different approval rules. I held a short workshop, wrote both needs side by side with the cost of each, and showed data on how often each case happens. They agreed on a rule with an exception path. I documented the decision and got sign-off." The point is facilitation, not taking sides.
38|I check the new request against the sprint goal and estimate its impact. I raise it with the product owner, who decides to swap it for something else or move it to the next sprint. If it must be added, it goes through a change request. I document it so scope is visible to everyone.
39|I first understand why it changed and the impact on design, development, testing and the date. I prepare two or three options with cost and time, such as accepting the change with a later date, a phased delivery, or keeping the old plan. I get written approval of the chosen option from the client before the team starts.
40|I use SQL to join tables, filter and group data, to check that a report matches the source, to find missing or duplicate records, and to understand data before writing requirements. I use Excel and a BI tool for charts. I do not write production code, but I need enough SQL to answer questions without waiting for a developer.
41|INNER JOIN keeps only rows that match in both tables. LEFT JOIN keeps all rows from the left table and the matching rows from the right, with NULL when there is no match. FULL JOIN keeps all rows from both tables, with NULL where there is no match on either side.
42|First I look at the data: counts, types, missing values and duplicates. I handle missing values by removing, filling or flagging them depending on the reason. I remove duplicates, fix data types and spellings, check outliers against business logic, and keep a log of every change so the work can be repeated and explained.
43|I use DENSE_RANK over a partition by department ordered by salary descending, and filter rank = 2: SELECT * FROM (SELECT dept, name, salary, DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) r FROM emp) t WHERE r = 2. DENSE_RANK handles ties correctly, while ROW_NUMBER would not.
44|I start with the question and the audience. Trends over time use a line chart, comparisons a bar chart, parts of a whole a simple pie or stacked bar with few items, relationships a scatter plot. I remove clutter, label clearly and put one key message in the title.
45|First I check data quality: a broken pipeline or a changed definition. Then I split the KPI by dimension: region, device, product, channel, customer type, and by time to see where the drop started. I compare with releases, campaigns and outside events. I report the cause with numbers and a suggested action.
46|I define the hypothesis and one primary metric, calculate the sample size and duration in advance, and split users randomly. After the test I check that groups are balanced, then the statistical significance and the practical size of the change. A significant but tiny change may not be worth shipping. I do not stop the test early because the result looks good.
47|Example (use your own): "Sales were falling in one region. I compared it to other regions, found that a delivery delay was causing cancellations, and showed the numbers to the operations head. They changed the courier and cancellations dropped [x] percent." Always end with the number that mattered and the decision it changed.
48|I ask three questions: who uses it, which decisions it should support, and which two or three numbers matter most. I build a small first version with those numbers, share it, and improve it with feedback. I tell the manager what is in the first version and what comes next.
49|I compare definitions first: gross or net, dates, filters, currency, refunds. Then I compare the data sources and the join logic and reconcile step by step to find the difference. I fix or document it and agree one official definition and source of truth with the owners.
50|Example (use your own): "I use SQL for extracting and checking data, Excel for quick analysis, Power BI for dashboards, and Python for cleaning large files. In [project], I used SQL and Power BI to show [result]." Choose one real project per tool and say what decision it supported.
51|CI/CD automates the path from commit to production. A typical pipeline: checkout, build, unit tests, static analysis and security scan, build a container image, deploy to staging, run integration tests, approval, then deploy to production with rollback. Tools could be Jenkins, GitHub Actions or GitLab CI.
52|A VM includes a full guest operating system on a hypervisor, so it is heavier and starts in minutes. A container shares the host kernel and packages only the app and its libraries, so it is light and starts in seconds. VMs give stronger isolation; containers give speed, density and consistency across environments.
53|I define infrastructure in Terraform modules, with separate state per environment stored remotely with locking. Changes go through pull requests; terraform plan is reviewed before apply. I use variables for differences between environments and run drift detection so manual changes are found.
54|I use rolling updates with readiness probes so traffic only goes to healthy pods, and set maxUnavailable to zero. For riskier changes I use blue-green or canary releases with a small percentage of traffic first. I keep the previous version for quick rollback and watch error rate and latency during the release.
55|I collect metrics, logs and traces. I define SLOs such as availability and latency and alert on symptoms users feel, not on every small spike. Alerts have clear owners and runbooks to reduce noise. Dashboards show the golden signals: latency, traffic, errors and saturation.
56|I run kubectl describe pod to see events and the last state, and kubectl logs --previous to see why the last container exited. I check wrong config or missing secrets, failing probes, out-of-memory kills from resource limits, and image or command errors. I fix the cause, redeploy and confirm that restarts stop.
57|Secrets are stored in a vault or the CI secret manager, never in code. Pipelines use least-privilege roles. I scan code, dependencies and images, sign artifacts, and require approvals for production. Runners are isolated and logs hide secrets, and every deployment is auditable.
58|Example (use your own): "A database ran out of disk and the app was down for 20 minutes. I freed space, restored service, and told stakeholders every 10 minutes. Afterwards I wrote a blameless post-mortem, added disk alerts at 80 percent and automated cleanup." Show timeline, fix and prevention.
59|Releases feel scary because they are big and manual. I make changes smaller and more frequent, add automated tests, use feature flags to separate deploy from release, and make rollback one click. I track deployment frequency and failure rate to show improvement.
60|I look at the cost explorer grouped by service, account and tag to find what grew. I check for idle or oversized resources, unattached volumes, extra data transfer and forgotten test environments. I ask the owner team, fix the waste, set budgets and alerts, and enforce tags for ownership.
